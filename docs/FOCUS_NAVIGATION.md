# Focus and remote navigation

The tvOS focus engine owns all directional movement in Bookworms. App code shapes movement through layout, focus sections, and entry preferences. It assigns no focus at launch or when a view opens from the sidebar. It assigns focus directly only at the entry events that [When app code assigns focus](#when-app-code-assigns-focus) lists, such as the return from a modal screen. Every remote press moves focus once, straight to its destination.

Read this guide before changing any view, control, or collection that can receive focus. See [tvOS views](../VIEWS.md) for what each view shows and [social views](SOCIAL_VIEWS_AND_AMBIENT.md) for rendering details.

## Why focus is structured this way

When a focused view handles a move command and also sets focus, the focus engine moves first, to the nearest item in the pressed direction. The handler then moves focus again. The user sees one item highlight briefly before focus jumps elsewhere without further input. Each additional handler, timer, or restoration path creates another way for focus to move twice, so the app has none of them.

## Navigation structure

The app's shell is a `NavigationSplitView` in [ShelfView.swift](../Bookworms/Views/ShelfView.swift). Its sidebar column is a `List`, and its column visibility starts at `.detailOnly`, so the sidebar is closed at launch and the focus engine's first choice is the selected view's entry item. Pressing Left from the leftmost content item or pressing Back opens the sidebar natively, with focus on the selected row, which the list's `.defaultFocus` names. On tvOS 27, Up from a view's topmost item opens it too. Select on a row shows that row's page and closes the sidebar; Right closes it and keeps the page. Either way, focus lands on the page's entry item in one focus update. The app never opens the sidebar or moves focus to it. It closes the sidebar once, when the app moves to the background, so that an app left through the open sidebar returns on its page.

While the sidebar is open, the page can't take focus. tvOS 27 takes the page out of the focus system. tvOS 26 leaves it in, where Right from a sidebar row would focus a far item before the closing sidebar moves focus to the entry item, so the shell disables the page while the sidebar is open. Left and Back open the sidebar from the focused item, so a page with nothing focusable would leave the sidebar unreachable, and Back would leave the app. Every state of every page therefore has a focus target: loading and empty states make their message focusable with `holdsFocus()`. [Sidebar focus at launch](investigations/sidebar-launch-focus.md) records why the shell is not a tab sidebar.

Two states in main content handle Back themselves. On a My Shelf that book details filtered by author or genre, which covers those details instead of replacing them, Back clears the filter and dismisses the shelf at once; the focus engine restores focus to the author or genre that applied the filter. In Book Wall details, which the wall draws in main content instead of presenting, Back closes the details and returns the book to the wall.

The sidebar is one list: the enabled main views, then **Ambient**, then **Settings**. Each row is a `NavigationLink` whose value is a private `SidebarItem`. The list's selection maps main views to `coordinator.current`; **Ambient** and **Settings** leave it on the last main view. A page is built again each time its row is selected, so state that outlives a visit lives in `BookwormsCoordinator`, `ShelfFocus`, or `BookWallScene`, not in the page's own state. **Settings** shows `SettingsView` in place, and Back returns to the sidebar. A row of section tabs in a header focus section, level with the collapsed sidebar, chooses the section; focusing a tab shows its section. They are buttons rather than a segmented control, which keeps Left at its leading edge, so Left from the first tab opens the sidebar. Each section lays out its controls in two columns. **Spines** has no controls and fits on one screen, so Down from its tab leaves focus on the tab; `SettingsInteractionTests` counts that and the tab moves around it. **Ambient** shows a page that holds the ambient choices and a **Start ambient mode** button, so selecting the row never starts playback. A `safeAreaInset` above the list shows the Hardcover profile; it takes no focus.

Each view divides its focusable content into focus sections with `.focusSection()`. A press aimed at a gap still reaches the section in that direction. Collections also declare `.defaultFocus(_:_:priority: .userInitiated)`, which chooses the item that receives focus when focus enters the collection from outside. A view whose collection sits below a header declares its entry item at the view's root too, because the focus engine otherwise enters the view at the header: Year in Review and Book Club name the remembered cover, and Compare Shelves names the row that focus last left, whose own default focus picks the book.

Book Wall preparation shows a modal when the current year's books are not ready. **Back to My Shelf** remains focusable while it loads; **Retry** appears if preparing a book fails. Back shows My Shelf too. With My Shelf hidden, the button and Back show the first other sidebar view instead, named on the button. When Book Wall is the only sidebar view, the modal has no button and Back selects **Settings**; the focus engine places focus in Settings. The modal shows only while Book Wall is the selected sidebar item. It closes when preparation finishes; closing it does not move focus into the wall.

The first-launch welcome popup keeps native modal focus during sign-in and download. Back from sign-in returns to the choices, whose default is **Connect Hardcover**. Back from the choices closes setup without marking it complete. During cover and shelf preparation, Back closes setup and marks it complete. The shell is disabled while the popup is open, so a view that mounts beneath it can't take focus from it. When the popup closes, the focus engine places focus on the view's entry item; the app assigns none.

Book Wall's noninteractive RealityKit canvas sits behind the split view and spans the screen. Focus controls stay on Book Wall's page. The view converts projected book rectangles from canvas coordinates to page coordinates, so the page's insets do not change the render viewport or move hit targets away from their models. The sidebar remains above the canvas. Leaving for another view, including Settings or Ambient, cancels any detail transition; stale task completions cannot reopen it.

Within a section, the focus engine picks the nearest item in the pressed direction. Up from a Compare Shelves row reaches the nearest header control, and Down from a Book Club cover reaches the nearest review action. Down where no item exists leaves focus unchanged.

## Paged collections

[`PagedRow`](../Bookworms/Views/ShelfView.swift) presents every horizontal collection. It keeps all items mounted (at most `BookLimit.maximum`, 40, and 20 in Feed) in one horizontal `ScrollView` with `.scrollTargetBehavior(.paging)`. Because the next page's items exist, the focus engine crosses page boundaries natively. `PagedRow` pads each item so that every page spans exactly one row width, and keeps items `PagedRowLayout.edgeInset` from each edge so that focus lift and shadows are not clipped. It scrolls to the page that contains `selectedID` and never assigns focus.

[`ShelfRow`](../Bookworms/Views/ShelfView.swift) wraps `PagedRow` for book shelves. My Shelf and both Compare Shelves rows use it. Layouts that pack pages must subtract `2 * PagedRowLayout.edgeInset` from the row width, as `ShelfView` and `SocialViews` do.

Items are keyed by their stable IDs in one flat `ForEach`. Repacking after a pause in input changes only padding, so a focused item keeps its identity and its focus.

## When app code assigns focus

The following entry points are the only places the app assigns focus. Each runs at an entry event: a modal screen or Book Wall's details opening or closing, or a press on **Retry**. None runs at launch, when a view opens from the sidebar, or in response to a directional press or a data change. A focus assignment made while the sidebar is open has no effect, because the page can't take focus then; `.defaultFocus` is what places focus when the sidebar closes.

| Event | Implementation |
| --- | --- |
| The shelf that book details filtered appears over them, or My Shelf appears beneath it when its filter is cleared | `ShelfRow` focuses its entry book in `onAppear` when `focusesEntryOnAppear` is set. tvOS 26 ignores `.defaultFocus` when a presentation opens or closes. |
| The user returns from details or ambient mode to a main view | `ShelfView.restoreSelection` issues a `ShelfBookFocusRequest` or advances `socialReturnRevision`. `SocialViews.restoreContentFocus` and `YearInReviewView` act only when nothing in the content has focus. |
| The user opens Book Wall details | The Back overlay focuses Back when it appears, as cover details focus Back first. |
| The user closes Book Wall details | `BookWallView.closeDetail` restores the selected spine after the return flight completes. A cancelled return does not assign focus. |
| The user selects **Retry** after a Book Wall graphics error | Retry connects a new renderer before the press finishes. When it runs, `BookWallView` focuses the entry spine, the remembered wall selection or else the first book, and **Retry** stays mounted until focus reaches the spine, so the press makes one focus update. When it fails again, focus stays on **Retry**. While the error shows, **Retry** is the wall's only control; Left and Back reach the sidebar. |
| The user opens or closes a full review in the book reviews popup | Opening a review disables the list, and the reader pane focuses itself when it appears. Back closes the reader; the list's default focus is the card that opened it, so the focus engine returns there without a focus write. |
| The user opens a series' books from the series pop-up's list | The books replace the focused row, so the books focus the current book, or the first, as they appear. Back returns to the list, whose default focus is the series that was open, without a focus write; focus passes through no item while the books leave, as when a pop-up closes. |

Data changes never move focus. When the first artwork preparation finishes, the loading message that held focus leaves, and the focus engine moves focus to the view's entry item. After that, content stays mounted while later preparations finish; covers reload from the local cache when `artworkGeneration` changes. Sorting, reader changes, and background refreshes update the mounted views in place.

## How to make changes

- **Add a view:** Group its controls into focus sections. Use `PagedRow` or `ShelfRow` for horizontal collections. Declare the entry item with `.defaultFocus(_:_:priority: .userInitiated)`, at the view's root too when a header sits above the collection. Give every state a focus target, with `holdsFocus()` on a message that stands alone. Add a navigation test for every direction out of every section, as described in [testing navigation](#testing-navigation).
- **Change which item receives focus on entry:** Change the value passed to `.defaultFocus`, such as `entryBookID` or `entryColumn` for `ShelfRow`.
- **Fix a direction that reaches the wrong item:** Change the layout or the sections. The focus engine chooses geometrically, so align the intended target with its source, or wrap the target group in `.focusSection()` so it catches presses aimed at a gap.
- **Add a modal screen:** Rely on native focus restoration after dismissal. If content needs a specific item afterward, issue the request from the dismissal callback and act only when nothing in the content has focus.
- **Add a control to a header:** Place it inside the header's existing `HStack`, which is already a full-width focus section.
- **Add a per-view choice:** Put it in that view's header, not in Settings, so users can change it without leaving the view. Settings holds the comparison limit, library, source, and app-wide choices.

`.onMoveCommand` is acceptable only for actions that do not change focus. For example, `ReviewReadingView` scrolls long reviews in response to Up and Down.

## Patterns to avoid

| Pattern | Problem | Instead |
| --- | --- | --- |
| Setting `@FocusState`, calling `resetFocus`, or requesting a focus update in `.onMoveCommand` | The engine moves first, so focus visibly moves twice. | Use layout, `.focusSection()`, and `.defaultFocus`. |
| Showing only the current page and swapping it on a boundary press | The next item does not exist, so the press escapes to the sidebar or header before code corrects it. | Use `PagedRow`, which keeps every item mounted. |
| Invisible focusable views that redirect focus when focused | They add a second focus update to every crossing. | Use `.focusSection()` or change the layout. |
| Timers or debounces on remote input | They hide a conflict instead of removing it and add input latency. | Remove the conflicting focus writer. |
| Searching the UIKit view hierarchy for a focus target, or adding `UIFocusGuide` bridges | Coordinates and view order change with system updates. | Rely on native sidebar and section behavior. |
| Moving focus in `onChange` or `task` in response to data, revisions, or loading completion | Focus moves while the user is idle or using another control. | Assign focus only at the entry events listed above. |
| Replacing mounted content with a loading view after the first load | Focus is destroyed and restored elsewhere. | Keep content mounted and update it in place. |
| Changing `.id(_:)` on a container that can hold focus | SwiftUI recreates its children and focus is lost. | Keep identity stable and change content. The shell's page is the exception: its identity is its sidebar row, and the page changes with the row either way. |
| A sidebar row that performs an action when selected | The list's selection names the page on screen, and an action has no page. | Make the row a destination page with a button, as **Ambient** is. |
| Assigning focus when a view appears in the split view | The page can't take focus while the sidebar is open, so the assignment is lost and focus enters wherever the focus engine chooses. | Declare `.defaultFocus` on the collection, and at the view's root when a header sits above it. |
| A page state with nothing focusable | Left and Back open the sidebar from the focused item, so the sidebar is unreachable and Back leaves the app. | Make the state's message focusable with `holdsFocus()`. |
| `.onExitCommand` in main content | It blocks Back from opening the sidebar. | Let Back use its native behavior. The filtered My Shelf that covers book details passes a handler, and My Shelf's page passes `nil`. Book Wall details handle Back only while they are open. |
| Tests that check only the final focused element | A bounce ends on a plausible item and passes. | Use `RemoteNavigation.press(_:in:expecting:)`. |

## Testing navigation

UI tests launch the app with `--focus-probe`. In Debug simulator builds, this installs `FocusTransitionProbe` from [ScenarioRuntime.swift](../Bookworms/Testing/ScenarioRuntime.swift). The probe counts `UIFocusSystem.didUpdateNotification` in an accessibility value without changing SwiftUI state.

[RemoteNavigation.swift](../BookwormsUITests/RemoteNavigation.swift) provides the shared helpers:

- `press(_:in:expecting:)` presses a direction, waits for the expected element, observes a one-second settle window, and requires exactly one focus update. A second update is a bounce.
- Its array overload accepts a small explicit set of valid destinations when native geometry allows more than one, such as Up from **Start ambient mode**, which sits below both Ambient columns. It still requires exactly one settled focus update.
- `pressWithoutMoving(_:in:from:)` requires zero focus updates where no item exists in that direction.
- `visibleButtons(_:prefix:in:)` returns fully visible items from left to right, because offscreen pages are mounted too.
- `open(_:arguments:)` launches on My Shelf and selects a view from the sidebar, which is how users reach every other view. Use it for view-entry tests. `launch(view:arguments:)` opens a view directly with `--start-view=`, which also adds that view to the sidebar if it was turned off. `selectView`, `focusSidebarItem`, and `openSettings` navigate through the sidebar.
- `moveFocus(to:in:)` presses toward a target from the focused element, changing columns before moving vertically. When Left or Right leaves focus in place, as at the end of a row that stops short of the target, it moves vertically instead. From the Settings section bar it presses Down first, because Left or Right would switch sections. Use it in two-column layouts such as Settings and the Ambient page.
- `hasFocus(labeled:in:)` checks sidebar rows and menu items by label, because they report focus on a container rather than on the element a name query returns. `waitForSidebarFocus(_:in:)` waits for a sidebar row to take focus this way, as after Left from a view's leading edge or Back.

The settle window is an observation period for late focus updates, not synchronization. Do not shorten it to speed up a test or lengthen it to make a failing test pass.

[ShelfNavigationTests](../BookwormsUITests/ShelfNavigationTests.swift) covers the launch on the first book with the sidebar closed, the return to My Shelf after leaving the app through the open sidebar, My Shelf, Year in Review, and book details with the series pop-up's list, checks, and books, [BookWallNavigationTests](../BookwormsUITests/BookWallNavigationTests.swift) covers native sidebar entry and return, counted spine/header movement, Back from the preparation modal to Settings in one focus update when Book Wall is the only sidebar view (`--test-only-book-wall`, `--test-wall-never-prepares`), repeated edge-book detail returns, a counted return from a filter its details applied (with no second flight and focus on the author), a counted return through details opened on another page of that filtered shelf (the page stays beneath them; focus on their book, then on the author), the filter's clear button returning to the whole of My Shelf, replay, on-screen focus targets, and, with `--test-wall-books=N` invented books, the page menu: its alignment with **Drop again**, counted movement around it, choosing a page with focus left on it, Down moving nothing while a page prepares and that page's arrival moving no focus (`--test-wall-slow-pages`), and returning from details on a later page. [SocialNavigationTests](../BookwormsUITests/SocialNavigationTests.swift) covers the social views. Use `openSettings`, `showShelf`, and `startAmbient` to reach sidebar destinations.

[ScenarioNavigationTests](../BookwormsUITests/ScenarioNavigationTests.swift) covers the welcome popup's default focus, both choices, and every directional boundary with `RemoteNavigation` focus-update counts. With a fictional example profile, it checks that the popup shows its preparation card while the example loads and that focus then reaches the first book in a counted number of updates, with the sidebar closed, Down reaches the status row's **Connect Hardcover** and goes no further, Up returns to the book, Left opens the sidebar, the sidebar lists Book Wall without social views, and Back from the example's sign-in returns focus to **Connect Hardcover**, on My Shelf and on a shelf an author filtered over the example's details. It also checks that focus enters the sign-in card on **New code** without a press, that **New code** keeps focus while it requests a replacement code, every direction from **New code** and **Get link code**, and, with the scenario's connected account, every direction in cover details of a Hardcover book and from the Ambient page's profile QR code toggle. The workflow cases cover Back, controlled authorization/download/preparation, failed downloads, and relaunch without repeating completed setup.

Simulator tests use discrete remote presses. Verify Siri Remote swipes, rapid input, and paging animation on the physical Apple TV.
